# 提交信息规范

> 适用于本仓库的**全部**提交：五份实现（C++ / GDScript / Node.js / C# / Python）、文档、测试、
> 构建脚本。
>
> 这是**约定式提交**（Conventional Commits）的裁剪版：保留「类型 + 范围 + 摘要」这个机器可解析的
> 骨架，摘要用中文写。**只有规范，没有强制工具** —— 为什么不装 commitlint 见 §7。
>
> 规范从 2026-11-02 起对新提交生效，**历史提交不改写**（§8 给了对照）。

## 1. 格式

```
<type>(<scope>): <摘要>

正文：为什么改、怎么改、验证了什么

BREAKING CHANGE: 不兼容的地方（可选）
Refs #12（可选）
```

- 第一行是**唯一必填**的部分。
- 第一行之后**空一行**，再写正文。
- 范围（`<scope>`）可省略，省略时括号一起省：`docs: 补充 STML 深度限制说明`。
- **类型与范围用英文小写，摘要与正文用中文** —— 前两者是给机器和 `git log` 扫的标签，
  后者是给人读的。

## 2. 类型

只有下面七种，**别自创**。不确定归哪类时按「这次改动对使用者意味着什么」判，不按「改了哪些文件」判。

| 类型 | 用在什么提交上 | 本仓库的典型改动 |
| --- | --- | --- |
| `feat` | 新增能力 | 新的实现、新模块、新公开 API、新语法支持、新指令 |
| `fix` | 修正与契约不符的行为 | 错误文案不对、五份实现不一致、实现与 golden 不符、越界/崩溃 |
| `refactor` | 行为**完全不变**的重构 | 改名、搬文件、拆函数、换内部数据结构 |
| `docs` | 只动文档 | `*.md`、注释里的说明 |
| `test` | 只动测试 | 用例、`golden_*.txt`、测试跑器 |
| `chore` | 仓库杂务 | `.gitignore`、CMake / `.csproj` / `package.json` 脚本 |
| `revert` | 回滚 | `revert: <被回滚那一条的首行>` |

两条容易判错的：

- **`refactor` 必须是行为不变**。顺手把错误文案从「nesting too deep」改成别的，那就不只是重构了 ——
  文案是契约的一部分（`*-test-plan.md` §7 的偏差表、golden 都跟着变），应该算 `fix`。
- **一次提交同时动实现和测试是常态**，按**被测代码**定性。例如「加深度上限 + 4 条 PR 用例」是
  `feat`，不是 `test`；只有「只补用例、实现没动」才是 `test`。

## 3. 范围

`<scope>` 是这次改动**主要**落在哪，不是文件清单。

| 范围 | 指 |
| --- | --- |
| `cpp` / `gd` / `js` / `cs` / `py` | 单份实现（目录名） |
| `lexer` / `parser` / `compiler` / `stml` / `vm` | 跨实现的某个模块 |
| `docs` / `build` / `repo` | 文档体系 / 构建 / 仓库本身（`.gitignore`、`.gitattributes`） |

约定：

- **五份一起改**时写主模块，并在摘要里注明份数：`feat(stml): 解析加嵌套深度上限（五份实现）`。
- 跨了模块又不属于任何一个（比如全库改名、全库改链接）→ 省掉范围。
- 范围用目录名/模块名，**不用** `core` / `misc` / `stuff` 这类无从判断的词。

## 4. 摘要怎么写

- **动词开头**：加、删、改、补、修、统一、拆、换、移。
- **一句话、不加句号**、不用「；」把两件不相干的事串起来 —— 串了就说明该拆成两条提交。
- **不超过 100 列**（汉字算 2 列，约 50 个汉字）。`git log --oneline` 一行放得下为准；
  在终端里折行了就是超了。
- **写具体的东西**：默认值、上限、涉及哪几份实现。别写「优化了一些细节」「修复若干问题」——
  三个月后自己都看不懂。
- 类型已经把「新增 / 修复」说过了，摘要直接说**加了什么**：`feat(stml): 嵌套深度上限，默认 256`
  比 `feat: 新增嵌套深度上限` 多带了默认值，首行有限的空间别浪费在重复上。

## 5. 正文与脚注

正文写三件事，每件一到三句就够，**不强求三段都写**：

1. **为什么改** —— 现象、动机、原来错在哪。贴得出错误输出就贴。
2. **怎么改** —— 关键决策，尤其是「为什么没用另一种更显然的做法」。
3. **验证了什么** —— 跑了哪几套测试、多少条断言。跨实现的改动必须写这一条。

格式要求：每行不超过 100 列，段落之间空一行，列清单用 `-`，行内代码用反引号。

## 6. 破坏性变更

本仓库有「标准」这个概念，所以**破坏性变更比一般项目多**。以下都算破坏，必须在类型后加 `!`
**并且**在脚注写 `BREAKING CHANGE:`：

| 变了什么 | 为什么算破坏 |
| --- | --- |
| `Program` 的字段、编码、opcode 编号 | 产物格式是三项标准之一；编号一动，手写执行器全得跟改 |
| 错误文案 | `syntax-reference.md` 与各 `*-test-plan.md` 的偏差表逐字引用它 |
| 五份实现的公开 API 签名 | 嵌进去的宿主程序要改代码 |
| STML 树的形状、属性语义 | 同上，属于标准 |
| 已有的语言 / STML 行为被改（不是新增） | 现有程序的结果会变 |

内置虚机（BasicVM）的接口**不随意调整**，所以动它的签名同样按破坏处理。

```
feat(compiler)!: PushValue 插到 PushBinArr 与 PushId 之间

原先把 `a = 1` 左侧的标识符也当值压栈，执行器要靠 AST 反推左值。改成压槽位后
执行器不用再判断，五份实现都简化了。

BREAKING CHANGE: `PushId` 之后的编号整体后移一位，33 起才是自定义指令。
依赖旧编号手写执行器的代码需要改。
```

## 7. 为什么不装 commitlint

仓库有一条硬约束：**零第三方依赖** —— nodejs 只用 ESM 标准库，C# 零 NuGet，Python 只用标准库。
`commitlint` + `husky` 要往仓库里塞 Node 包和 git hook，和这条冲突：clone 下来想提交，先得
`npm install`。

单人维护的项目里，它防的「格式漂移」本来就不容易发生；真发生了也是 `git log` 一眼能看出来。
等出现下面任一情况再引入，规范本身不用改：

- 有第二个人开始提交；
- 要靠提交历史自动生成 CHANGELOG 或判定版本号（`semantic-release`、`release-please`）。

在那之前按 §9 自查三条命令就够。

## 8. 历史提交怎么算

规范只对**新**提交生效。已有的历史提交基本都是中文自由格式，**不重写** —— `git rebase`
改历史换来的是所有哈希失效，收益为零。对照一下就知道差在哪：

| 历史提交 | 按本规范 |
| --- | --- |
| `STML 解析加嵌套深度上限（默认 256，0=不限），五份实现一致` | `feat(stml): 解析加嵌套深度上限，默认 256、0=不限（五份实现）` |
| `demo 改为「教用法」而不是「对齐输出」；统一内置 BasicVM 的稳定性表述` | 拆两条：`docs: demo 定位改为教用法，不追求跨实现输出一致` + `docs: 统一内置 BasicVM 的稳定性表述` |
| `创建了 Node.js 实现的项目。 修改了 C++ 实现的 Lexer、Parser、Compiler 的构造器，添加了 Reset 函数。 …` | 至少拆三条，且首行不该塞三句话（176 列） |
| `4d0f061 chore: 初始化 stope-lang 仓库` | **已经合规** —— 仓库唯一一条带类型的提交 |

结论：这次规范加的东西主要是**类型前缀**和**首行字数**，其余（中文、动词开头、正文讲为什么）
仓库本来就在做。

## 9. 提交前自查

三条命令，都不需要装东西：

```bash
git log --oneline -5     # 首行是不是一句话、终端里有没有折行
git log -1 --pretty=%B   # 空行有没有、有没有句号、脚注格式对不对
git diff --cached --stat # 这一条是不是混了两件不相干的事
```

第三条如果看着别扭（比如 `src/` 和 `docs/` 各改了一堆、彼此无关），就拆成两条提交。
**测试要先跑过**再提交，各实现的跑法见各目录的 `README.md`。
